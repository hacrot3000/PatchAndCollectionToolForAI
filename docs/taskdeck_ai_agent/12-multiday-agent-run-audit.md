# Agent Chat multi-day Collection/Patch audit and interruption risk register

Audit date: **2026-11-21**. Source of truth: `hacrot3000/PatchAndCollectionToolForAI`, current `main` (audited at `3031e9d3b00ecde0998deb8ec029d6817ca50066`) plus the fixes in this audit branch.

## Status update — 2026-11-21 (PR #162)

- **P0 false milestone completion closed for tool evidence:** The task planner no longer accepts an acknowledged Native Patch with FAIL/PREFLIGHT_FAIL/INCOMPLETE or an error-bearing Collection as successful evidence. Explicit native PASS and successful Collection observations are required; an independent test run remains a separate criterion.
- **Objective Auto-check added:** a user-scoped, revision-fenced, explicitly approved exact `call_id` rule can automatically accept a narrowly machine-verifiable PASS Patch wrapper or complete, error-free file read. The tool's actual owner-scoped canonical/archived receipt is checked; no extra provider request or native re-execution is performed.
- **Archive-heavy continuity improved:** each rule tracks its last-inspected Collection/Patch archive generation. A new archive segment wakes one re-evaluation, preventing missed evidence without creating a continuous disk-scan loop.
- **Still P0:** Semantic functional test verification, provider authoritative acknowledgement for SENDING/UNKNOWN, and durable fair multi-day worker scheduling. See [handoff 17](17-objective-task-evidence-autocheck.md) and [PR #162](https://github.com/hacrot3000/PatchAndCollectionToolForAI/pull/162) (merged as `90a5ca769857004e23db0433ad3103251e7c56a9`).

## Status update — 2026-11-21 (PRs #160–#161)

- **R-02 partially mitigated by PR #160:** TaskDeck now records exact prepared provider payloads and a durable `PREPARED → SENDING` egress boundary. It can autonomously resume a previously unsent, checksummed `PREPARED` request after restart. **SENDING/UNKNOWN remain non-replayable** until provider acknowledgement is authoritative.
- **R-08 partially mitigated by PR #161:** a canonical, owner-edited plan tracks up to 128 acceptance-gated milestones, tool/attested evidence, progress and completion independent from an AI turn. User-opted-in Auto continue invokes the existing native approval/idempotent provider paths and halts after repeated model-only nonprogress. **It does not independently evaluate semantic acceptance or mark milestones complete without trusted evidence.**
- **R-05 partially mitigated by PR #161:** provider admission failures before network egress now use durable exponential retry-after rather than a three-second polling loop. Post-egress errors remain subject to the acknowledged/unknown recovery boundary.
- **Handoff and CI:** see `docs/taskdeck_ai_agent/16-durable-task-plan-orchestration.md`; PR #161 Agent Chat protocol core PASS. Further research still required for authoritative provider acknowledgement and multi-day fairness.

## Status update — 2026-11-21 (PR #158)

The original risk table below is a historical baseline as of the first audit. Changes landed subsequently in [PR #158](https://github.com/hacrot3000/PatchAndCollectionToolForAI/pull/158):

- **R-01 partially mitigated:** up to 125 sequential, fully acknowledged completed Native Patch calls were verified with persistent owner-scoped Patch archive segments and minimal provider-context summaries. The live 32-record limit remains intentionally for calls that are pending, running, rejected without final acknowledgement, or otherwise ambiguous; do not call it unlimited for those cases.
- **R-02 partially mitigated:** daemon startup marks orphaned `requesting_ai` as interrupted/failed with a durable event; a `sending` Patch result becomes `FeedbackStatus=unknown`. This removes the stuck `requesting_ai` state, **but does not autonomously resume/replay an uncertain provider call**.
- **R-03 still unresolved:** exact provider acknowledgement for uncertain feedback egress requires provider-specific reconciliation/idempotency or an explicitly approved manual recovery.
- **Context policy improved:** new standalone `internal/agentchat/contextcompact` selectively preserves recent full Collection observations subject to a configurable safe token share; older read-only evidence becomes path/file summaries and past completed Patches become minimal receipts. The exact new Patch/Collection output is unmodified; the canonical journal is never truncated merely to fit the model request. Provider-side conversation reference chains still need a deliberate stateless rebase to guarantee remote context pruning.
- **Handoff:** see `docs/taskdeck_ai_agent/13-context-compact-and-multiday-handoff.md` for final commit, tests and next coding request.

**Remaining release gate:** safely recover/reconcile provider egress and long-running job state across restart (R-02/R-03). A complete multi-day autonomous Patch workflow is not yet guaranteed.

## Scope and conclusion

A task may involve hundreds/thousands of read-only **Collection** requests interleaved with many **Native Patch** proposals and verified feedback. The Collection loop is unlimited by *number of rounds*, but **a task is NOT yet guaranteed to run autonomously for days**, especially across a process restart or large numbers of Patch operations.

This document distinguishes fixes implemented now from risks **recorded but not resolved**. Do not describe a risk as fixed merely because an individual numeric limit has been removed. Native Patch always uses its existing authorization and project/workspace checks; don't blindly replay native side effects.

## Outstanding risks — recorded, NOT implemented in this audit

| ID / priority | Exact interruption scenario / code evidence | Suggested resolution / acceptance criteria |
|---|---|---|
| **R-01 / P0** | **33rd Patch in one conversation cannot be saved**: `internal/agentchat/store.go:validateSession` rejects `len(x.ToolCalls)>32`. It also requires every Patch call to remain in live `x.History`. Only older Collection observations are archived today (`history_archive.go`). Native Patch tasks involving dozens/hundreds of independent code changes eventually fail. | Design an append-only **Patch-call archive**, preserving exact immutable call/arguments, approval snapshots, native run receipts, feedback and audit association; archive only terminal/fully acknowledged calls; keep pending/unknown calls live. Remove the 32 limit only after both archive and owner-scoped retrieval are tested. Regression: 1000 serial Patch calls; error, rejection and ambiguous approval; crash between archive and session commit; no duplicate native execution. |
| **R-02 / P0** | **TaskDeck process crashes/restarts while `requesting_ai`**: a provider in-flight turn is process-owned (`agent_chat_messages.go` + `agent_chat_retry.go`), while startup reconciliation (`agent_chat_sync.go`) only adopts native Patch results. The durable status can remain `requesting_ai` with no active worker, and the new-message endpoint refuses that status. A background scheduler scans Patch states, not orphaned model continuations. | Durable per-turn lifecycle with a lease, heartbeat, resumable job cursor, and explicit `recovering/needs_attention` state on startup. Reconcile provider acknowledgement by ID where supported. Never resend an ambiguously delivered Patch result or run the same native Patch twice; require a user decision when exact-once delivery cannot be proven. Test kill/restart at every journal/egress boundary. |
| **R-03 / P0** | **Patch result sent but provider acknowledgement unknown**: `agent_chat_tool_feedback.go` marks `FeedbackStatus=unknown` and exits when transport fails or process shuts down. Existing behavior correctly avoids duplicate side effects but leaves autonomous workflow stopped. | Implement a provider-aware acknowledgement lookup / idempotent continuation protocol, or a UI/manual recover-send workflow that preserves exact `call_id` and verified receipt. Never automatically replay an unknown provider egress without evidence. |
| **R-04 / P1** | **Auto-feedback may expire after 30 minutes** for legacy `/auto-feedback` grants (`agent_chat_auto_feedback.go:agentAutoFeedbackMaxAge`). The newer Automation menu's **persistent Auto-send results** uses `AutoFeedbackPersistent`, but old sessions/mixed settings may stop when Patch finishes later. | Migrate legacy settings or display TTL/expiry clearly; for explicitly opted-in multi-day automation use persistent permission with revocation. Test a Patch finishing after 24–72 hours. |
| **R-05 / P1** | **Provider may return non-retryable error / quota or model unavailability**, or user configured retry **Off**/**5 times**. `agent_chat_retry.go` limits retries by mode, and providers impose independent constraints even with unlimited Collection. An unlimited retry also consumes API budget if provider continually fails. | Surface distinct statuses `retrying/rate_limited/blocked/needs_attention` and a user-controlled time/cost budget; bounded exponential backoff with Retry-After; a safe resume action after configuration/model repair. Test 429, 503, connection loss and key rotation over days. |
| **R-06 / P1** | **Active sessions/archives grow on disk**. `history_archive.go` creates new private JSON archive files and `Store.Save` syncs to disk. Disk-full, filesystem outage, power failure, too many files or per-archive >4 MiB will stop persistence. Old archived content is inspectable via internal `ArchivedCollectionHistory` but does not yet have a dedicated user-facing evidence browser. | Disk free-space health check, archival rotation/compaction and recovery from orphaned segments; owner-scoped UI/export for past exact evidence; retention and backup policy; chaos test out-of-space and torn writes. |
| **R-07 / P1** | **Tasks needing interactive approval / shared-server ownership**. Auto Patch is intentionally local-owner only, off by default; persistent Auto-send results is a separate explicit setting (`agent_chat_session_automation.go`). A pending approval waits indefinitely for a person, especially with an expired or changed worktree snapshot. | UI status `waiting_for_approval` and an opt-in alert/reminder. Use the existing approved local automation flow when appropriate. Never bypass per-call approval on shared servers. |
| **R-08 / P1** | **No workload-independent progress/liveness detector for the entire plan**. Collection may be unlimited but the model may voluntarily reply after partial research, repeatedly propose incomplete patches, exhaust task context, or do no useful work. The current identical-read warning detects only a narrow loop, not task completion. | Persist a durable task plan, task IDs, state machine, milestones/checkpoints and acceptance gates. Require explicit terminal states `completed/blocked/needs_approval`; separate workflow orchestration from a single model HTTP exchange. Track evidence/progress per task before scheduling next. |
| **R-09 / P2** | **Per-session context/replay limits remain real**: `internal/agentchat/responses.go` caps provider history items and request bytes; `Store.Save` caps active session bytes; long Patch histories cannot currently be archived. `maxSessionEvents=128` retains only the latest transition markers (not a full event audit). | Integrate Patch archives with active context compaction. Keep immutable full event audit in an append-only event log, and send scoped summaries + last relevant evidence to the model; never silently delete Patch evidence. |
| **R-10 / P2** | **Background workers limited to four** (now intentional). If all four spend days on long provider continuations, other sessions wait, although the scheduler itself remains responsive. Multiple daemons share neither admissions nor an authoritative distributed scheduler; source comments specify one daemon per workspace. | Queue with FIFO/fair priorities and durable worker leases; display position/age of waiting jobs; add distributed coordination only when multi-daemon deployments are supported. |
| **R-11 / P2** | **Browser or reverse-proxy connection can time out** during a very long synchronous API response. | **R-12 / P2** | **One native Patch retry record permits at most 8 stored attempts** (`validateSession`). Test more than eight explicit reapplications of a failed Patch without losing audit data. |

## Required multi-day acceptance test plan

1. **Collection-heavy:** 10,000 paged, varied read requests; repeat/narrow on large outputs; valid JSON, stable UTF-8, no dropped user goal and no growing active-session memory.
2. **Patch-heavy:** 1000 independent Patch proposals and native final receipts (PASS, FAIL, rejection), with Auto Patch/Auto-send enabled by an authorized local user; verify ownership, exact feedback pairing, no duplicate execution and bounded active memory.
3. **Cross-process:** kill/restart before provider egress, during provider response, after Collection Save, during Patch queuing, after native execution and before/after feedback acknowledgement. Restore safely without inventing a success or automatically replaying unknown side effects.
4. **Faults:** disk full, permission failure, 429/503, provider timeout, unavailable model, changed API credentials, missed UI polling and a disconnected browser.
5. **Multiple conversations:** one session stuck in multi-day retry must not block reconciling/auto-feedback for other sessions; verify scheduler fairness with more than 32 and 64 sessions.
6. **Completion:** a durable task checklist and validation/test gates must prove the original user goal is actually met, not merely that the Collection loop ended.

**Release decision:** Collection-only research can keep running without an arbitrary round cap while the daemon and provider remain healthy. **Unattended multi-day Collection+Patch is not yet production-guaranteed** until R-01, R-02 and R-03 are resolved. Keep those explicitly tracked rather than disguising them with a larger numerical limit.
